## 2. Smart Contract — SplitPay.sol

### ✅ What works correctly
- Atomic USDC distribution to 2–10 recipients in one tx
- OpenZeppelin SafeERC20 (v5.1.0, Paris-compatible)
- Manual reentrancy guard (`_locked` bool)
- Basis-point arithmetic (10,000 = 100%)
- Rounding: floor per recipient, remainder to last recipient
- Post-distribution invariant: `sum(amounts) == totalAmount` (not griefable by external sends)
- All custom errors with descriptive names
- `previewSplit()` pure function for frontend preview
- 42 unit tests passing (happy path, reverts, events, fuzz, invariant)
- Balanced security audit: no High/Medium findings (both auditors clean)

### ⚠️ Limitations / honest disclosures
- Max 5 recipients in prompt spec, but contract allows 10 — **frontend should cap at 5 per spec**
- No onchain nonce/revoke registry — scheduled payment signatures cannot be cancelled onchain
- `DistributionError` is reused for both reentrancy and arithmetic failure — separate errors would be clearer
- No version or upgradeability mechanism (intentional for this MVP)

### 🔴 Mismatch: chain vs contract
- `useSplitPay.ts` uses `arcTestnet.id` (5042002) as CHAIN_ID
- `splitpay-config.ts` has the ETH Sepolia deployed address
- The contract was deployed to ETH Sepolia with ETH Sepolia USDC
- **Arc Testnet faucet cap prevented Arc Testnet deploy**
- Result: frontend points at Arc Testnet but contract is on ETH Sepolia → every transaction fails

- TR/EN language switching
- About page
- Scheduled payment UI (create/sign/execute/cancel)

3. **No persistent state**: tx history, scheduled orders all lost on page refresh

12. **Subkey labeling**: presented as if it enforces onchain restrictions, but current contract has no `verify(sig)` — must be clearly labeled "off-chain signature only, beta"

## 4. Subkey — Honest Assessment

**What "Subkey" currently is:**
- An EIP-712 typed-data signature generated by the user's wallet
- Stored only in React state (lost on refresh)
- Restrictions embedded in the signature message: contract, chain, amount, recipients, dates, nonce
- **The current SplitPay contract does NOT verify this signature** — execution calls `splitPay()` directly with the original signer as `msg.sender`
- The signature acts as an authorization record / audit trail only, not as onchain enforcement

**What this means for users:**
- The time window restriction IS enforced — `executeOrder` checks `now >= executeAfter && now <= expiry` in the hook (off-chain check)
- A malicious relayer could technically call `splitPay` with different parameters — there is no onchain sig verification
- Onchain cancel/revoke is impossible without contract upgrade

**For the permissions UI:**
- Show only restrictions that are actually enforced (dates checked off-chain in hook)
- Clearly label which restrictions are off-chain only vs contract-enforced
- Recommend a future `ScheduledSplitPay.sol` that calls `ecrecover` to verify the EIP-712 sig onchain
